# Context 契約保証と ReactionEnd / Result 統合の検討

記録日: 2026-11-07

Parrot 移行後の振り返りを受けた設計検討の記録です。
ユーザーの検討方針と、それに対するエージェントの意見を区別して残します。
コード生成は未実装です。後続の合意と未決定事項は
[Analyzer と Context 引数ジェネレーターの計画](./ANALYZER_AND_CONTEXT_GENERATOR_PLAN.md) にまとめています。ReactionEnd の Result 保持と InteractionEnd の Context 保持廃止を試行しました。
現行仕様は [Reaction とフローの結果](../REACTION_RESULTS.md) を参照してください。
以下の検討記録は変更前の背景を含みます。
必須値取得の最小 API として GetRequired<T>() と専用例外を追加しました。
現在の運用は [文脈値の取得](../CONTEXT_VALUES.md) を参照してください。

## Context の契約保証

### 問題提起

[TalkToParrot](../../InteractionFlow.Samples.Parrot/Interactions/TalkToParrot.cs) は IFlowContext を受け取りますが、
実行には SampleMode が必要です。ParrotGreeting は任意です。
[ParrotApplication](../../InteractionFlow.Samples.Parrot/SystemFlows/ParrotApplication.cs) がそれらを追加します。
この提供側と要求側の対応は、現在は構成コード、TryGet、実行時の例外から読み取ります。

小さなサンプルでは追えますが、必要な値や合成経路が増えると、提供忘れや有効範囲の追跡が難しくなります。
IFlowContext は概念上の Context の System 側への投影であり、Context Loop そのものではありません。
ここで検討するのは、この実装上の値の契約です。

### ユーザーの検討方針

Context の契約保証をコードジェネレーターで支援することを検討中です。
生成方式、宣言形式、保証範囲はまだ決定していません。

### エージェントの意見

方向として有望です。柔軟な Context の合成を残しつつ、要求する値を明示し、取得処理の反復を減らせます。
ただし、取得アクセサーを生成するだけでは、呼び出し元が値を提供した保証にはなりません。
生成されるコードと、コンパイル時に検査できる範囲を分けて設計することが重要です。

最初の対象は「必須値と任意値の区別」「要求の一覧化」「一貫した取得・検証」に絞ると評価しやすいと思います。
構築用 API も生成して必須値を型で要求すれば、生成 API を通る経路ではより強い保証が可能です。
一方、任意の IFlowContext、手動 With、動的な親探索を許す経路には、実行時検証が残ります。

確認したい点は次のとおりです。

- 必須値の不在と、任意値の不在・既定動作を区別できるか。
- FlowContext の値の上書きと親へのフォールバックを維持できるか。
- RefEntry など可変な保持値と、値そのものの要求を区別できるか。
- 静的に検証できない経路を、保証済みと見せかけず診断・実行時検証へつなげられるか。
- 生成によって、値の共有期間や非同期実行の安全性まで保証したと誤解させないか。

まず Parrot の SampleMode と ParrotGreeting で試し、宣言量と利用コードの読みやすさを比較するのがよさそうです。
新しい Context DSL 全体を先に作るより、具体的な要求から生成範囲を広げる方が過度な抽象化を避けられます。

## ReactionEnd と Result

### 問題提起

Parrot では出力ごとに ReactionEnd.HasException を確認し、失敗時に後続処理を止めています。
失敗確認の反復が多く、Result の連結 API と表現を共通化する余地があります。

また、標準のキャンセル処理は、待機・リセット・通知に成功すると成功の ReactionEnd を返します。
したがって「キャンセルが処理できた」と「ユーザーがメニューを終了したい」は異なります。
SelectSample は OnCancellation で ExitRequested を保持し、SystemFlow が進行を判断します。

### ユーザーの検討方針

ReactionEnd 周りについて、Result との統合を検討中です。
統合の対象が内部表現、操作 API、公開型そのもののどこまでかは未決定です。

### エージェントの意見

成功・失敗の表現と連結方法を共通化する方向には利点があります。
ただし、次の三つは独立した判断として扱う方が安全です。

1. 内部の成功・失敗表現を Result にそろえる。
2. ReactionEnd に Result と共通の変換・連結方法を提供する。
3. 公開型を統合し、ReactionEnd を Result に置き換える。

1・2 だけでも重複を減らせる可能性があります。
3 では、現行の「Reaction による終了結果を生成する」という境界をどう保つかが課題になります。
現在は ReactionEnd の internal コンストラクタ等が生成元を制限し、InteractionEnd が実行時の Context と結び付けます。
任意の Result をそのまま終了結果として使えるようにすると、生成元の制約は変わります。
その変更を意図するか、明示的な境界変換で残すかを決める必要があります。

### 特に確認したい意味の違い

[Result API](../RESULT.md) を現行契約の基準として、次を検討します。

- Result の失敗は ResultException で包まれます。現在の ReactionEnd.HasCanceled は例外を直接
  OperationCanceledException と比較するため、単純な格納形式の置換ではキャンセル判定が変わります。
- Result に格納された失敗、送出された例外、キャンセルされた Task は異なります。
  統合後も、Result のコールバックや委譲先の例外を勝手に捕捉する契約へ変えないことが重要です。
- キャンセル処理の成功は、アプリ全体や会話の終了指示とは別です。
  Result へ統合しても、この区別が自動的に解消されるわけではありません。
- ExitRequested のような進行意図は、アプリ側の Context や明示的な結果値として保持する設計が候補です。
  すべての正常終了へ汎用的な終了理由を追加する必要があるかは、実例から判断します。
- 値なし Result の default は成功です。公開型統合では生成元の制約に加え、既定値の意味も確認します。

エージェントとしては、まず内部表現または境界変換を試し、Parrot の失敗確認とキャンセル分岐が
実際に読みやすくなるかを比較する進め方を支持します。
反復を減らすための連結が、入力待ち・文字送り・早期終了をかえって読みづらくしないかも評価対象です。

## 検討時の比較材料

Context は必須値不足、任意値不在、専用挨拶のスコープ終了を確認します。
Result 統合は出力失敗後の停止、元例外の保持、キャンセル処理成功後のメニュー復帰、
メニューでの終了意図の保持を比較します。
これらを維持しながら、利用側の宣言と分岐が減るかを評価します。

# EscapeGameの利用側改善プラン

状態: 実装前の計画。ライブラリ拡張案とは分離する。
対象はEscapeGame・そのテスト・関連文書。Core / Standard / Analyzerのコードと公開契約は変更しない。

## 判断基準

必要な責務分離、薄いInteraction、明示登録、ポーズ時の二重確認を欠陥として削除しない。
意味が明確になり、変更時の調査とテストが容易になる修正を優先する。
新しい抽象・割り当て・同期を増やす案は、小さな変更で代替できないか先に確認する。

## 段階1: 終了処理の暗黙契約を明示する

GameCancellationHandlingがWith<Result>の存在から終了処理中と判断する仕組みを、
サンプル内の明示的な終了処理情報（先行Resultと処理種別）へ置き換える。
CloseWindow / EndSession / GameSystemFlow / WindowSystemFlow / 両Handlerを確認対象とする。
通常停止の回復とClose/EndSession自体のキャンセル失敗を区別し、先行失敗を保持する。
値の存在判定だけで通常処理の意味が変わらないことを検証する。
コストは小～中。終了経路だけの値で、毎フレームの割り当てを増やさない。
新しい終了情報はClose/EndSession専用の独立/子スコープだけへ登録し、通常セッション・フレームへ漏らさない。
通常Contextに無関係なResult.Successまたは失敗Resultを追加しても、キャンセルの意味が変わらないことを検証する。
CloseとEndSessionの双方で、送出・キャンセル・リセット失敗と先行失敗の組合せを確認する。

## 段階2: 内部の不成立と通常の無効操作を区別する

GameReactionのMutationStatus処理を整理する。
選択のRejectedは通常のフィードバック、Deferredは同じ仕事の保持、Stoppedは終了として維持する。
初期化・確定済み行動・敵行動・結果表示など、フローの前提違反によるRejectedは
黙って成功として返さず、明確な実行障害として扱う。提示を必要とするAppliedでkeyがない場合も同様。
各操作について合法な戻り値を列挙してから変更し、停止・ポーズ競合を誤って障害化しない。
Beginの未公開セッション例外を、waitBeforeApplyという切替値より明示的な初期化経路で表す。
共通化は状態更新後の提示待機等の機械的部分に限定する。
コストは小～中。正常経路の追加割り当てを避ける。

| 操作と不成立の例 | 扱い |
| --- | --- |
| 選択の無効入力・条件不足 | 通常のRejectedとフィードバックを維持 |
| Beginの二重公開、確定なしのApplyPlayer | 内部前提違反として失敗 |
| 提示未完のApplyEnemy、勝敗未確定のShowResult | 内部前提違反として失敗 |
| EnableSelection/EnableResultInputの段階・提示条件違反 | 内部前提違反として失敗 |
| 任意の更新でPaused / Stoppingが成立 | Deferred / Stoppedを維持し、前提違反と混同しない |

上記の直接不正呼び出しは実際のGameReactionを使って検証する。
Appliedなのに提示keyがない等、sealed Contextから任意注入しにくい状態は、
小さなinternal検証関数の直接テストまたは生成構造による保証で確認する。
テストのためだけにContext・アクセス管理の新しい差し替え機構を増やさない。

## 段階3: 進行確認と結果保持を読みやすくする

Turn/SessionSystemFlowのCanContinueAsync重複を、サンプル内の内部補助へ抽出するか検討する。
方針が同じ部分だけを共有し、フローからポーズ・停止・失敗の分岐が読み取れることを優先する。
Access側のActive再確認は残す。フロー側の確認だけで原子的更新を保証しない。
失敗集約は小さな内部補助で統一を検討し、通常Result連結と混同しない。
例外の捕捉範囲を拡大せず、既存の例外同一性・集約内容・順序を確認する。
コストは小。汎用フロー基底やDSLは導入しない。

## 段階4: アクセスの責務と寿命の見通しを改善する

IGameWorldAccessとEscapeAccessのメソッドを利用箇所ごとに整理し、
セッション寿命・選択/行動・進行参照の契約分割に実効性があるか評価する。
すべてを機械的に別interfaceへ分割せず、依存が減り呼び出しが明確になる範囲だけ採用する。
共通の同期境界は維持し、Contextを受け取るPortが最小権限になるとは主張しない。
アプリとセッションで同じContext型を使う前提、SessionId=0の扱い、
独立Cancellationと親共有の生成方法を、名前・コメント・テストで明示する。
必要ならサンプル内ID型を検討するが、提示キー等の既存識別を全面変更することを目標にしない。
コストは中。新しい管理オブジェクト・ロックの追加は避ける。

## 任意検討: Functionと1対1対応するInteractionの粒度

ApplyPlayerAction等の一行委譲を、薄いという理由だけでは廃止しない。
一方、Functionのメソッドごとに機械的にInteractionを作っていないか、段階2～3の後に一覧で確認する。
各Interactionの目的、完了範囲、SystemFlowからの呼び出し位置、分岐・ポーズ確認の必要性を対応付ける。

- 同じ目的・完了範囲で、途中にSystemFlowの選択や他の相互作用との合成が不要なら、
  一つのInteractionから複数Functionを呼ぶ構成への統合を検討する。
- 独立した行動・提示待機・制御経路としてSystemFlowが選ぶ単位は維持する。
  ポーズ操作をゲーム側の入力・提示待機へ取り込まず、独立制御を保つ。
- 統合によりキャンセル登録の範囲、OnCancellation、処理Portへの委譲、失敗時の短絡、
  Reactionの完了範囲、フロー境界の再開確認が変わる場合は、その影響を検証する。
- Interactionの直接ネストや、SystemFlowからFunctionを直接実行して明示Reactionの境界を迂回する解決は採らない。
- 共有インスタンスの可変な「現在の処理種別」で複数Interactionを代用しない。
  汎用ディスパッチやデリゲート化でフローから目的が読めなくなるなら採用しない。
- ファイルをまとめるだけの整理は、Interaction数の削減とは区別して評価する。

現行契約では、独立した一回の相互作用が一つのFunctionへの委譲で完結する場合もある。
意味のある境界を保ったまま改善できないなら、現状維持を妥当な結果とする。
本項は対応必須ではなく、見送る場合も理由を記録する。ライブラリ原則やAPIは変更しない。
採用時はフローの可読性・変更箇所・テスト容易性と、必要に応じ実行時コストを比較する。

## 段階5: ナビゲーションと検証の整理

READMEに一操作の呼び出し経路、Context生成と所有、完了範囲をまとめる。
ForceResetや明示Dependency等の必要な定型コードは維持する。
テストの提示完了・入力配送・終了の準備を、同じ意味の範囲で共有する。
実際の更新規則と同じ実装をテスト補助へ複製せず、競合順序と外部観測を検証する。
ライブラリへテスト支援を追加せず、サンプル内の補助にとどめる。

## 各段階の受け入れ条件

- 12ターン脱出と両捕獲、リトライ、結果提示後の受付が維持される。
- 受理済み入力・確定要求の保持、ポーズ中の更新/時間/ack抑止、再開後の一回適用を維持する。
- 古いセッション・提示の通知/省略を拒否し、入力の蓄積を導入しない。
- 起動前停止、提示/入力/再開待機中の停止、Stop失敗時のcancel/join/closeを維持する。
- Close/EndSessionの送出・キャンセルでも先行失敗を失わない。
- 変更に対応する回帰テスト、影響範囲のビルド・テスト、意味が変わる段階では全体テストを行う。
- Release簡易計測を変更前後で比較し、フレーム実行とスナップショットの割り当て増加を確認する。
- 入力・描画経路を変更した場合は実画面で操作・ポーズ・再開・リトライ・終了を確認する。

各段階はレビュー・指摘修正・再レビュー後にコミットする。
段階4の大きな分割は、段階1～3の後に実際の変更箇所を見て採否を決める。
今回は計画作成までで、実装はまだ行わない。

## 元の指摘との対応と対象外

暗黙の終了判定は段階1、行動結果と実行成功の混同・初期化例外は段階2、
進行確認重複と失敗集約は段階3、広いWorld契約とセッション識別・Context寿命の見通しは段階4、
多層の追跡とテスト準備の負担は段階5で扱う。
明示Reaction、各Portの完了範囲、Function分類と所有関係は文書・テストでも明示する。
薄いInteractionの一律廃止は対象外とし、意味に基づく任意の粒度見直しは上記の範囲で扱う。
依存宣言の自動化、型による完全な権限制御、全状態の自動同期、
汎用的な全体ポーズ、描画環境への無変更移植、Interactionの実行固定費削減は対象外とする。
これらは意図した責務、別のトレードオフ、またはライブラリ変更を要する検討であり、今回の未達欠陥とは数えない。

## プランレビュー

サブエージェントが現行コードと照合し、段階1～2優先と段階4の条件付き採用を妥当と評価。
終了情報のスコープ限定、通常Resultからの意味独立、Rejectedの具体的分類、
不正な提示結果を検証する手段の指摘を反映した。ライブラリ実装の変更は行わない。

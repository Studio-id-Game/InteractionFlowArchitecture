# Interaction 実行の計測と改善計画

記録日: 2026-11-09。対象コミット: `d088936`。
当初の記録は計測用コードと計画のみです。その後、第1段階を実装しました。
以下の当初計測は対象コミット時点の値で、末尾に実装後の比較を記録しています。

## 計測方法と範囲

[計測プロジェクト](../../benchmarks/InteractionFlow.ExecutionMeasurements/Program.cs) は
ソリューションに含めない、外部パッケージ追加なしのコンソールプログラムです。
実際の Interaction 基底と PresentFrame を使い、raylib の入力と描画を fake Port に差し替えます。
参照先は Raylib サンプルですが、ネイティブ API は呼びません。

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run --project benchmarks/InteractionFlow.ExecutionMeasurements -c Release
```

環境は .NET 10.0.14 / x64、SDK はリポジトリの global.json。
各ケースを20,000回ウォームアップ後、200,000回ずつ3回測定しました。
時間は Stopwatch、割り当ては GC.GetAllocatedBytesForCurrentThread の差分です。
GC の明示実行は計測区間の前に行います。初回のキャンセル状態生成と登録 List の拡張は定常計測から除外します。
プロセスの初回起動コスト、実描画、ThreadPool 待ち時間、競合、p99 フレーム時間は対象外です。
時間値はマイクロベンチマークの目安で、各オブジェクトの時間を加算して全体時間を推定しません。

中断ケースは、未完了の本体 Task を返してから呼び出しスレッド上で完了させます。
本体 TCS の継続を意図的にインライン実行し、呼び出しスレッド上で全実行が完了したことを検証します。
これは「await が中断した経路」の測定であり、実際の非同期 I/O や別スレッド実行の測定ではありません。
例外・キャンセル経路は今回の性能測定には含めず、最適化時の契約回帰検証で必須とします。

## 実測値

以下は段階的 JIT を無効にした同一実行の3回の結果です。

| ケース | 時間範囲 ns/回 | 割り当て B/回 |
| --- | ---: | ---: |
| 成功 ReactionEnd の取得 | 3.6–4.6 | 0 |
| InteractionEnd の生成 | 6.8–11.7 | 24 |
| Task.FromResult(ReactionEnd) | 6.1–19.6 | 72 |
| 完了済み Task を await して返す async ラッパー | 9.6–10.9 | 72 |
| 完了通知 TCS の生成と完了 | 26.3–27.3 | 96 |
| 既存 CancellationObject への登録・解除 | 30.5–31.4 | 40 |
| コンパイラー生成キャプチャの単独生成 | 5.0–6.0 | 48 |
| 最小 Interaction、本体 Task を毎回生成 | 108.1–111.5 | 496 |
| 最小 Interaction、本体 Task を事前共有 | 104.3–106.0 | 424 |
| 制御された本体中断と完了 | 383.6–391.0 | 712 |
| フレーム本体を直接実行 | 94.9–97.0 | 0 |
| PresentFrame.ExecuteAsync | 212.2–213.3 | 496 |

キャプチャ単独生成は、現在のコンパイラー生成型を reflection で特定して、事前コンパイルした
生成関数で測っています。reflection と式のコンパイル自体は計測外です。
生成型が変わった場合、この診断はスキップします。公開契約として生成型名やサイズを固定しません。

本体 Task を共有したケースは、72B の寄与を確認するための対照実験です。
本体や結果を一般にキャッシュしてよいことを意味しません。
中断ケースの712Bには、本体側で生成する TCS も含みます。

## 同期完了時496Bの内訳

[Interaction.Generic.cs](../../InteractionFlow.Core/Interactions/Interaction.Generic.cs) の通常経路と、
上記の構成要素計測・対照実験から以下の内訳に整合します。全体のヒープトレースではありません。

| 要素 | B/実行 |
| --- | ---: |
| ExecuteCoreAsync が返す Task | 72 |
| AwaitBodyAndCleanupAsync が返す Task | 72 |
| ExecuteBodyAndSignalCompletionAsync が返す Task | 72 |
| 公開 ExecuteAsync が返す Task | 72 |
| 完了通知の TCS と内部 Task | 96 |
| TaskRegistration | 40 |
| InteractionEnd | 24 |
| ローカル関数が共有するキャプチャオブジェクト | 48 |
| 合計 | 496 |

成功 ReactionEnd は共有済みで、通常成功時の新規割り当てではありません。
CancellationState / CancellationTokenSource は通常実行ごとに作り直していません。
現在の毎フレーム処理は同期完了し、フレームごとのスレッド切り替えもありません。

## 第1段階: 公開 Task 契約を維持して同期完了経路を整理

最優先です。IInteraction / Interaction<TContext> の公開・protected シグネチャは変更しません。

1. 開始前キャンセル確認と完了通知の登録は、本体呼び出しより前に維持する。
2. 本体 Task を受け取り、IsCompletedSuccessfully なら同期経路で結果を処理する。
3. 通知を完了し登録解除して、InteractionEnd を Task.FromResult で返す。
4. 未完了 Task と失敗 Task は専用の非同期処理へ渡し、通常経路の不要な async ラッパーを外す。
5. 同期経路ではキャプチャを作らず、非同期ヘルパーへ必要な引数を明示的に渡す。

注意点: faulted/canceled の完了済み Task を成功経路へ混ぜません。
同期送出は呼び出し側へ新たに漏らさず、既存どおり処理 Port へ渡します。
ExecuteCoreAsync 呼び出し時の同期キャンセル例外と、返された Task のキャンセルを区別します。

2つの内部 Task とキャプチャを除去できれば、同じ本体を前提に
496 - 72 * 2 - 48 = **304B/回**が初期目標になります。
これは未実装案の概算で、達成値ではありません。性能よりも既存契約の維持を優先します。

## 第2段階: ValueTask 契約の採否を別判断

第1段階の計測後、必要なら公開実行と本体を個別に検討します。
公開側を ValueTask<InteractionEnd> にできれば同期時の72B、本体も ValueTask<ReactionEnd> なら
さらに72Bを削減できる可能性があります。前段の仮定では232B、160Bの順になります。
TCS・登録・終了結果の160Bは残るため、戻り値だけで割り当てゼロにはなりません。

戻り値変更は既存の派生実装、直接interface実装、呼び出し側の Task 利用、合成、テストに影響します。
互換層を残す場合、AsTask の位置によって割り当てが復活します。
同名メソッドを戻り値だけで併存させることもできません。
API の簡潔さと移行負担を評価してから採用を決め、今回は変更しません。

## 第3段階: 完了通知を必要時に具現化する内部契約

第1・第2段階で不足する場合だけ検討します。
本体開始前に軽量な実行登録を行い、リセットで待機が必要になったときに通知 Task を生成する案です。
登録を本体実行後へ遅らせる案とは異なります。

開始とリセットの競合、完了との同時アクセス、後始末失敗の保持、待機対象確定後の解除を扱うため、
CancellationObject の内部プロトコルの再設計になります。単純なTCS遅延生成だけでは成立しません。
一般公開の AddCancelableTask 契約は維持できるかも含めて検討します。
オブジェクトの再利用・プールは、旧登録と新世代の混同や参照寿命の問題が増すため初期案に含めません。
InteractionEnd の共有・値型化も同一性や利用コードへの影響を別途評価し、初期案に含めません。

## 各段階で守る契約と検証

| 経路 | 必須の確認 |
| --- | --- |
| 同期成功 / 非同期成功 | 明示Reactionの結果を保持、登録解除、同じContext、Context非所有 |
| 開始前キャンセル | 本体とOnCancellationを呼ばない |
| 本体の同期送出 | 既存のPortへ委譲。同期キャンセルでOnCancellationを呼ばない |
| 本体 Task のキャンセル | OnCancellation完了後、通知完了、CancellationPortへ委譲 |
| 後始末の失敗 | 待機側への失敗保持・収集、元キャンセルとPort失敗の保持 |
| 処理Portの送出 | 未処理例外の伝播、通知の失敗を観測、登録を必ず解除 |
| リセット中の開始 | 本体開始前に登録を拒否 |
| 待機対象の確定後 | 登録解除後も確定した対象を待つ、旧世代を新世代へ混ぜない |
| 多重実行 | 同じInteractionインスタンスでも実行ごとの状態を独立させる |

検証は既存のInteraction / CancellationObjectテストと型付き契約テストを基準にします。
追加の競合テストはTCS等で順序を制御し、時間待ちへの依存を避けます。
各段階で全体ビルド・テストとこの計測を再実行し、同期完了だけでなく中断経路の増分も比較します。
ThreadPoolや競合の測定を追加する場合は、全スレッド割り当てと待ち時間を扱う別の計測にします。
呼び出しスレッドの割り当てだけを実行全体の割り当てとして報告しません。

## 第1段階の実装結果

公開API・本体のprotected契約を維持し、2つのローカルasync関数をExecuteAsyncへ統合しました。
同期成功時はIsCompletedSuccessfullyから結果を取得し、それ以外は同じメソッド内でawaitします。
別の非同期ヘルパーへ分離するより小さな変更で、内部Taskとキャプチャの除去を達成できました。
公開メソッド自体はasyncのまま維持するため、同期送出も従来どおり返却Taskの結果へ反映されます。

本体開始前の登録、OnCancellation対象の区別、後始末の失敗保持、通知完了後のPort委譲、
finallyによる登録解除は維持しています。キャンセル登録方式や終了結果の同一性は変更していません。

当初と同じ方法・環境のRelease計測結果です。

| ケース | 変更前 B/回 | 変更後 B/回 | 変更後 ns/回（3回範囲） |
| --- | ---: | ---: | ---: |
| 最小Interaction・本体Task新規 | 496 | 304 | 93.9–101.0 |
| 最小Interaction・本体Task共有（対照） | 424 | 232 | 88.4–89.2 |
| 制御された中断と完了（本体TCS含む） | 712 | 448 | 171.2–176.5 |
| フレーム本体の直接実行 | 0 | 0 | 89.4–90.8 |
| PresentFrame.ExecuteAsync | 496 | 304 | 183.0–187.0 |

同期経路は192B（約38.7%）削減し、304Bの初期目標を達成しました。
本体Task72B・公開Task72B・通知TCS96B・登録40B・InteractionEnd24Bが残ります。
completionを保持するキャプチャ型は検出されなくなり、単独生成診断はスキップされます。

既存の例外・キャンセル・後始末テストに加え、同じContext/Interactionへの多重実行で
同期成功が別実行の登録を解除しないこと、同期本体と処理Portの送出を返却Taskに保持することを検証しました。
第2段階以降は未実装です。次に進める場合は、残るコストとAPI移行の負担を比較して採否を判断します。

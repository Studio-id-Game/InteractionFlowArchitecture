# ライブラリの保証拡張と開発支援の検討

記録日: 2026-11-09。
状態: CounterとEscapeGameによる検証を踏まえた検討記録。候補のAPI名・配置・導入順序は未確定です。
本書の新機能は未実装であり、現行契約を変更しません。

## 1. 目的と責務の境界

利用者が定義した相互作用と実行方針を、正しく・読みやすく実現するための機械的な処理を支えます。
[哲学](../PHILOSOPHY.md)の「コードの構造とユーザーが経験する構造を近づける」方向と、
[計算モデル](../COMPUTATIONAL_MODEL.md)の「Interactionは状態遷移、SystemFlowは合成と選択」の分担を基準にします。

| 区分 | ライブラリが担うこと | 利用者に残すこと |
| --- | --- | --- |
| 保証の拡張 | 利用者が明示的に採用した契約について、生成・伝播・追跡・待機・識別等を正しく実装する | 何を実行するか、結果の意味、停止条件、状態の不変条件 |
| 責務履行の補助 | 設計・記述・テスト・調査・既知の誤用検出を支援する | 仕様と期待値、整合性の境界、補助の適用範囲の判断 |

二つは関連します。例えば完了通知の補助を採用すれば、その通知の一回性は補助APIが保証できますが、
通知を発行するべき業務上の時点までライブラリが決めるものではありません。
保証は採用したAPIと登録した対象の範囲に限定し、未登録の処理や利用者の状態全体へ拡張しません。

構成量、薄い転送クラス、ポーズの協調処理等が存在すること自体は、ライブラリの保証違反ではありません。
改善余地を考えるときも、意図された責務と、不要な機械的負担を区別します。

## 2. 評価基準

以下のコスト・効果は現時点の設計上の見積もりで、開発時間や新APIの性能を実測したものではありません。

| 基準 | 確認する内容 |
| --- | --- |
| 意味の明示性 | 何を実行し、何を待ち、どう応答・終了するかをコードから読み取れるか |
| 実装・維持コスト | 初期実装だけでなく、競合検証・互換性・保守に見合うか |
| 実行パフォーマンス | 割り当て、ロック、スケジューリング、同期完了経路への影響 |
| 実開発効率 | 記述だけでなく設計・調査・テスト準備・修正の時間を減らせるか |
| 再利用性 | ゲームの段階や特定の描画環境を知らずに成立するか |
| 選択可能性 | 必要な利用者だけが採用でき、未使用の構成へ負担を加えないか |

クラス数や行数の削減だけでは評価しません。複雑さを隠した結果、挙動の説明や調査が難しくなる案は慎重に扱います。
Coreは概念と契約、Standardは再利用可能な任意利用の実装とし、テスト・開発ツールも役割に応じて分けます。
汎用性を確認する前に、サンプル固有の状態管理をCoreへ移しません。

## 3. 保証を拡張する候補

| 候補 | 想定する保証 | 配置候補 | 実装コスト | 実行時コスト | 開発効率への寄与 |
| --- | --- | --- | --- | --- | --- |
| ReactionEnd<T>のみの導入 | Reactionが確定した型付き結果と、値なし結果への変換の一貫性 | Core | 小～中 | 型の表現・変換次第。要計測 | 高 |
| 実行を所有するスコープ | 登録実行の追跡・合流・失敗観測、閉鎖後の開始拒否 | まずサンプル、次にStandard | 中～高 | 管理・同期の負担。任意利用 | 高 |
| 失敗集約の補助 | 明示的に渡された複数の失敗を欠落させずResultへまとめる | Standard等。既存Result APIとの整合を確認 | 小～中 | 成功経路を軽くできる | 中～高 |
| 識別付き完了通知 | 古い通知の拒否、一回性、閉鎖時の待機解除 | まずサンプル、次にStandard | 中 | 待機時のTCS等。要計測 | 高 |
| 任意利用の実行診断 | 開始・終了・キャンセル・失敗の一貫した観測点 | Coreの接続点と任意の実装を検討 | 中 | 無効時の負担を特に確認 | 中～高 |

### 3.1 実行を所有するスコープ

EscapeGameのWindowSystemFlowは、開始、Task保持、停止、キャンセル、合流、失敗集約を手で構成しています。
利用者が並行対象・停止条件・停止方法を定義した後の、追跡・待機・結果観測には共通化の価値があります。

- 開始と登録の競合を扱い、本体を開始した後で初めて追跡するだけの仕組みにしない。
- Taskの正常完了と返却Resultの成功を区別し、業務結果の解釈は利用者へ残す。
- 停止方法や兄弟実行への失敗伝播方針を、利用者が明示できるようにする。
- 未登録の処理やキャンセル非対応処理を強制停止できるとは保証しない。
- 全対象を待つことと、有限時間で必ず終了することを混同しない。
- 明示Reactionを経ずにInteractionEndを生成する仕組みにしない。
- SystemFlowから合成と寿命を読み取れる形を保ち、Contextへ実行管理を集約しない。

通常経路の記述削減より、失敗・競合時に繰り返し実装する手順を減らせるかを評価します。

### 3.2 失敗集約

現在のResult連結APIによる条件付きの連結と、独立した後始末の結果を集める用途は区別します。
初期案は、渡されたResultや例外を明示的に追加し、成功・単一失敗・複数失敗へまとめる小さな補助です。
例外の自動捕捉や、キャンセルの自動成功化、業務上の失敗の解釈は初期案に含めません。
既存の失敗を再ラップ・欠落させないこと、集約の構造と順序を説明できることを確認します。

### 3.3 識別付き完了通知

Counterの入力待機とEscapeGameの提示待機には、古い後始末・通知の遮断、重複通知、終了時の解除という共通点があります。
世代やチケットで待機対象を識別する小さな部品として抽出できる可能性があります。
「画面が提示された」「行動が完了した」という意味は利用者が定義し、部品は対応関係と通知寿命を保証します。
UI全体の完了保証や汎用イベントバスへ広げず、実際に共通化できる範囲を先に検証します。

## 4. 利用者が責務を履行するための補助候補

| 候補 | 補助すること | 実装コスト | 実行への影響 | 開発効率への寄与 |
| --- | --- | --- | --- | --- |
| 非同期フローのテスト支援 | 開始・保留・完了・キャンセル・失敗の順序制御、呼び出し履歴 | 中 | 製品実行へ持ち込む必要なし | 非常に高い |
| 状態・寿命のガイドと実例 | 不変条件、共有範囲、完了範囲、終了手順の整理 | 小 | なし | 高 |
| 協調的な再開待機 | ポーズ待機、再開通知、閉鎖、世代の扱い | 中 | 待機・同期の負担 | 中～高 |
| 対象を絞ったAnalyzer | 解放漏れやInteraction直接ネスト等の既知の誤用検出 | 中～高 | 主に開発時 | 高 |
| コード修正・生成支援 | 依存転送や定型入口、Contextアクセスの記述 | 中～高 | 生成方式次第で小さい | 中 |
| 実行トレースの表示 | どのフロー・相互作用が何を待つかの調査 | 中 | 任意有効化・サンプリング | 中～高 |

### 4.1 テスト支援

今回有用だったのは、提示を保留したまま描画を続ける、確定とポーズの順序を入れ替える、
次の提示へ移った後に旧通知を配送する、停止Portを失敗させる、といった検証です。
制御可能な非同期処理・履歴・失敗注入・ValueTask単一消費確認等の足場を毎回作る負担を減らします。
ゲーム状態の期待値は利用者が定義し、テストフレームワーク依存をCoreへ入れない方針とします。

### 4.2 ポーズ補助の限界

再開待機だけでは「Active確認→ポーズ成立→状態更新」の競合は解消しません。
待機・通知・閉鎖を補助しても、ゲーム更新と制御状態の確認を同じ整合性境界で扱う責任は利用者に残ります。
これを「全フローを自動で安全に停止する保証」と表現しません。
異なる用途でもう一度使い、共通化できる部分を確認してから抽出します。

### 4.3 Analyzer・生成支援・診断

[既存計画](./ANALYZER_AND_CONTEXT_GENERATOR_PLAN.md)の、判断可能な構文に絞る方針を維持します。
解析不能と規約違反を区別し、状態全体や全実行経路を保証したとは扱いません。
APIが安定する前に検査・生成対象を広げず、型付きInteraction導入後のContext引数生成の必要性も再評価します。
既存APIで自然に書けるものを別の宣言方式へ置き換えるだけなら優先度を上げません。
診断は無効時の追加割り当て等を測り、Contextの不要な保持や毎フレームの高負荷を避けます。

## 5. ReactionEnd<T>に限定する案

### 5.1 目的と範囲

Reactionが確定した値を、同じInteraction内の後続処理へ型付きで渡します。
結果伝達のためだけにContextへ一時値を書き込む必要を減らせます。
InteractionやSystemFlowの外へ型付き結果を伝える拡張とは分けて評価します。

| 項目 | 最小案 |
| --- | --- |
| 新しい終了型 | Result<T>を保持するReactionEnd<T> |
| 生成 | Reaction側だけが生成できる型付きAPI |
| 既存契約への接続 | 非ジェネリックReactionEndへ値を除去する明示変換 |
| 変更しない契約 | InteractionEnd、Interactionの実行契約、SystemFlow、共通例外・キャンセルHandler |
| Contextとの分担 | 共有する現在の状態はContext/State、一回の応答が確定した値は型付き結果 |

例は未実装APIの利用イメージです。WithoutValueという名前は仮称です。

```csharp
var response = await reaction.RespondAsync(context, command);
if (!response.Result.Try(out var decision, out _))
    return response.WithoutValue;

return await nextReaction.RespondAsync(context, decision);
```

型付きReactionを最後にする場合も、値を除去した終了結果を返して既存InteractionEndへ接続できます。
値を取り出しただけで相互作用を終了したことにせず、既存契約どおり明示Reactionに基づいて終了します。
返却された失敗Resultと、送出例外・非同期結果のキャンセルを混同しません。
送出された例外・キャンセルは現在と同じInteraction基底の処理を通るため、共通HandlerにTを要求しません。

### 5.2 便利になる用途

選択への応答、確認・承認、入力や編集の確定、作成・保存後のIDや情報など、
Reactionの後にその確定値を使う処理がある場合を想定します。
Operationが取得値を返すだけなら既存の戻り値で足ります。データ取得を型付きReactionへ機械的に置き換えません。
観測可能な応答を提供するReactionの意味と、型付きの確定値を対応させます。

位置や扉等の共有状態は引き続きStateに保持します。
両方へ保持する場合、Stateは現在、終了値はその相互作用の完了時点の報告として区別します。

### 5.3 契約で詰めること

- 非ジェネリックReactionEndはsealedです。Resultプロパティを隠す継承より、独立した型と明示変換を第一候補にする。
- 利用者が任意の場所で終了結果を新規生成できる公開コンストラクター・暗黙変換を増やさない。
- 型付き生成APIの名前、Result<T>を渡す方法、既存GetEndとのオーバーロード解決を確認する。
- 値除去で成功・失敗・元の例外を保持する。失敗を再ラップしたり成功へ変換したりしない。
- Result<T>のnull成功値禁止・Exception成功値禁止・default未初期化失敗の契約を引き継ぐ。
- 型付き終了結果の値が参照型なら、その内部可変性や状態更新の原子性まで保証しない。
- 型付き結果の生成と値除去の割り当てを測定する。成功ReactionEndの共有が現在と同じように使えるとは仮定しない。
- class/struct、変換の表現、生成・変換の配置等は未決定であり、計測と契約テストから選ぶ。

検証では、成功値・失敗・未初期化Result<T>、値除去後の同一失敗、生成制約、
Interaction内の中間Reactionと最終Reaction、送出例外・キャンセルの既存Handlerへの伝播を確認します。
新旧のReactionを併用でき、値なしのフレーム描画へ不要なコストを持ち込まないことも確認します。

### 5.4 InteractionEnd<T>まで広げる案との違い

| 観点 | ReactionEnd<T>のみ | InteractionEnd<T>まで接続 |
| --- | --- | --- |
| 主な用途 | Interaction内でReactionの確定値を利用する | 呼び出し元やSystemFlowが相互作用の結果から次を選ぶ |
| 実行契約 | 現行を維持できる | 結果型付きInteraction/SystemFlow等の検討が必要 |
| 共通Handler | 現行の値なし結果でよい | 回復成功時のTを誰が決めるかが問題になる |
| 合成 | 最終的に値を除去して既存の終了型へ接続 | 異なる結果型の合成と最終Reactionによる確定を設計する |
| コスト | 小～中。変更範囲を限定できる | 中～高。API・実装・移行の範囲が広い |

広い案では、リトライ/終了等をSystemFlowへ直接返す価値がありますが、今回は対象外です。
共通Handlerの回復成功にdefault(T)を補うことや、Reactionを経ずSystemFlowが終了結果を自由生成する変更は避けます。
まず小さい案の有用性を確認し、必要性が出た段階で別途判断します。

## 6. 推奨する進め方

1. ReactionEnd<T>のみの最小契約を具体化する。Coreの型表現の拡張として、小さい範囲で検証する。
2. テスト支援と失敗集約を初期候補にする。本番の実行負担を増やさず、反復作業の軽減を確認する。
3. 実行所有スコープをサンプル内で試し、SystemFlowの意味が明示されたまま停止・合流の負担を減らせるか確認する。
4. 通知識別と再開待機を異なる用途で使い、共通部分が確認できたものからStandardへ移す。
5. 安定した契約にAnalyzer・コード修正・必要な生成支援を付ける。

この順序は推奨案です。今回の文書化だけで導入や実装開始を決定したものではありません。
各候補はサンプルでの変更範囲、テスト準備、レビューでの不具合、実行時の割り当て・時間を比較して評価します。
行数削減と保守コストの増加が相殺していないか、意味の不明瞭な回避策が減るかも確認します。

## 7. 現時点で責務を広げない範囲

状態全体の自動同期・トランザクション・ロールバック、全処理の自動ポーズ、ユーザーの認識保証、
Contextへの実行管理の集約、フレームループ・スレッド方式の一律指定は初期候補にしません。
汎用フローDSL・スケジューラーや、性能だけを目的にした複雑なプールも、必要性の実測なしに導入しません。

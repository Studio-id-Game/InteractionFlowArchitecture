# InteractionFlowを使うアプリケーション設計

Raylib counter の改修で固まった、InteractionFlowのAPIを生かすための設計指針です。
ゲームを主な想定例としますが、描画ライブラリの種類には依存しません。
描画環境固有の方針は [描画ライブラリとの接続設計](./RENDERING_LIBRARY_INTEGRATION.md) に分けています。

規範の入口は [設計思想](../PHILOSOPHY.md)、[ライブラリ実装](../LIBRARY_IMPLEMENTATION.md) と個別契約です。
以下の「基本方針」は利用設計の基準です。「適用条件」「Counterの例」はサンプル固有の判断を含みます。

## 1. 状態・コンテキストを設計の土台にする

ユーザーが何を行い、何が応答し、次に何が可能になるかを要件として把握したうえで、
具体的な設計は **状態・コンテキスト → SystemFlow → Interaction → Port契約** の順に進めます。
状態設計は、後続の進行・相互作用・機能契約を判断する根拠になります。

| 順序 | 決めること | 次の設計へ渡す前提 |
| --- | --- | --- |
| 状態・コンテキスト | 現在の状況、可能な操作、遷移、不変条件、所有・寿命・共有範囲 | どの状況で何が可能で、何を守る必要があるか |
| SystemFlow | 状態に応じた相互作用の選択・反復・合成・終了 | 次に何を実行し、どの結果から経路を決めるか |
| Interaction | 一回で達成する目的、入力から明示Reactionまでの処理と完了範囲 | 必要なFunctionと、その実行順序 |
| Port契約 | 必要な入力・応答・外部機能の引数、結果、失敗、非同期性 | 実装・差し替え・検証の境界 |

これは設計を進める主な方向です。Portや描画環境の制約、非同期処理から前提の不足が見つかったら、
状態設計へ戻って見直します。最初にすべてのクラスやAPIを確定する必要はありません。

### 状態設計で明らかにすること

保持するフィールドに加え、次の内容を書きます。

- 現在の段階と、それぞれで受け付ける操作。
- 遷移の条件と、関連する複数の値で守る不変条件。
- 選択・行動の確定・取り消し・失敗・終了で何が変わり、何が残るか。
- 状態の所有者、寿命、共有範囲、読み手と更新者、整合性が必要な更新単位。
- ユーザーに示す状況と、実行管理・描画・演出のために保持する内部情報。

例えば「終了要求後に入力受付へ戻らない」「鍵の消費と扉の解錠は一緒に成立する」といった条件です。
これらが、フローの分岐条件、Interactionの処理範囲、Portが提供する操作の粒度へつながります。

最初に設計するContextは、ユーザーとSystemが共有する状況です。
概念上のContextと、文脈値を提供する実装上のIFlowContextは区別します。
まず状況と遷移を整理し、その前提からStateの分割、アクセス契約、FlowContextによる提供方法へ具体化します。
一つのFlowContextインスタンスや、すべての状態を格納したクラスを最初から作ることを意味しません。

### State・アクセス管理・Contextの分担

状態が増えたときは、次の二つを使い分けます。

- 一つのState内部をヘルパーで構造化する: 一緒に扱う責務の実装を読みやすくする。
- 関心別にStateを分割する: 各機能が必要とする状態・操作の依存を分ける。

分割した関心同士は、必要な値や協調相手を引数で明示して連携できます。
共有更新の整合性を保つ必要がある場合は、アクセス管理が複数Stateを同じ同期境界で扱います。
interfaceやクラスを分けることと、ロックを分けることは同じではありません。

| 要素 | Counterでの例 | 責務 |
| --- | --- | --- |
| State | CounterState / CounterDisplayState | 値と規則。同期処理やTask管理を持ち込まない |
| アクセス管理 | CounterAccess / CounterInputWait | 安全な読み書き、関連Stateの一括更新、入力通知との協調 |
| Context | CounterFlowContext | アクセス契約や文脈値の提供、追加値の制約、スコープ構成 |

Contextを実行エンジンにせず、進行判断・Task起動・キャンセル待機を詰め込みません。
TryGetの呼び出し中だけロックしても、取得後の可変Stateへのアクセスは保護できません。
並行共有する状態は、安全な操作を提供するアクセス契約を通し、生の可変Stateを持ち出させない構成を検討します。
単一スレッドに限定したStateまで一律にラッパーとロックを追加する必要はありません。

可変参照型のStateなら、そのプロパティ更新のためだけにRefEntryで包む必要はありません。
RefEntryは保持する値そのものの差し替えが必要なときに選びます。

### 専用Contextの契約を型で表現する

SystemFlow<TContext> → Interaction<TContext> → 専用Contextを受け取るPort、という経路を使えます。
提供するアクセスを用途別interfaceのプロパティにすると、依存が型の宣言から読めます。
TryGetCoreもそのプロパティを返し、共通HandlerからのGetRequiredと同じ値を提供します。
公開したくない内部のアクセス管理型まで取得できないよう、要求型の範囲を明示します。

固定プロパティには破棄済み確認を入れます。破棄後の新規取得を禁止することと、
すでに取得した共有値を無効化することは別です。共有先への影響と所有権は明記します。

プロパティと追加値探索の結果を一致させる必要がある場合は、ValidateAdditionalValueを使います。
With<object>など元の宣言型以外での登録と、後から変化するEntryも検討対象です。
Counterは3つの固定アクセス契約と全Entry派生値を拒否しますが、これは専用Context固有の方針です。
全ContextにEntry禁止を広げず、通常のFlowContextの子へ親の制約を伝播させません。

親ありContextは親のCancellationを共有します。独立したキャンセルが必要なら、
共有アクセスだけを受け渡す別ルートを明示的に構成します。何を共有し、何を継承しないかを文書化します。
Withの戻り値はFlowContextなので、専用型の変数宣言と追加値の登録は分けます。

## 2. 状態に基づいてSystemFlowを設計する

状態ごとの可能な操作と遷移を前提に、Interactionの選択・反復・合成と体験の終了条件を決めます。
進行のために参照する状態と子から受け取る結果を明らかにし、正常・キャンセル・失敗の経路を整理します。

### 検証を進める方向: 実行間の依存関係と寿命を構成する

SystemFlowは、逐次実行に加えて、体験の進行に関わる並行実行の合成にも活用できます。
何を並行させ、どの結果を待って次へ進み、どの条件で停止して全体を完了するかを記述する場所として検討します。
選択・反復・終了判断と合わせて、実行間の依存関係と寿命を構成する役割を重視します。
これは今後のゲームサンプルで検証する設計方針であり、すべての並行処理をSystemFlowへ集約する規則ではありません。

| 設計すること | 確認する内容 |
| --- | --- |
| 開始と実行順序 | 並行させる処理、先行結果が必要な処理、実行スレッドの制約 |
| 合流と次の経路 | 全実行・特定の実行のどちらを待つか、結果から何を判断するか |
| 終了と失敗の伝播 | 一方の終了・失敗・キャンセル時に、他方を継続するか停止するか |
| 終了待機と結果集約 | 誰が実行を所有し、何の完了を待ち、どの失敗を全体結果へ保持するか |

Counterでは、WindowSystemFlowがメインスレッドでフレームを進めながら、
Task.RunでCounterSystemFlowを起動し、終了要求・停止・終了待機・結果集約を調整しています。
この構成により、各Interactionは個々の相互作用に集中できます。

Taskやスケジューラーは実際の実行機構で、SystemFlowはその利用方針と体験上の合成を記述します。
SystemFlow基底が自動で並行化・キャンセル伝播・全実行の終了待機を保証するものではありません。
状態の不変条件と所有・共有範囲を前提に、共有アクセスの同期はアクセス管理へ、
一つの機能内部の非同期処理はそのFunctionへ置き、全体の合成と区別します。
次のサンプルでは、並行・合流・停止の方針をフローから読み取れるか、
終了時に未所有の実行や循環待機が残らないかを確認します。

| 要素 | 基本方針 |
| --- | --- |
| Program | Profile適用、Scope/Context構築、ルートフローの起動、プロセス終了結果の受け取り |
| SystemFlow | Interactionの選択・合成・反復、体験の進行と終了、実行の寿命の調整 |
| Interaction | 一つの目的のためにFunctionを接続し、明示Reactionの結果で終了 |
| ExternalPort | 利用側から必要とする機能の契約 |
| External | Portの実装と実行環境への接続 |
| Entities | 外部環境に依存しない値、状態、計算、遷移規則 |

Programに入力・描画・ゲーム進行を残さず、SystemFlowで表現できる流れはそこで記述します。
Interactionから別のInteractionを直接実行せず、合成はSystemFlowで行います。
SystemFlowも長い一つの手続きにせず、起動・反復・停止・終了など意味の単位でprivate関数へ分けます。

## 3. フローの各段階をInteractionへ具体化する

SystemFlowの各段階について、一回の相互作用で達成する目的と、その前後の状態を決めます。
操作受付の条件、行動確定の時点、Operationから明示Reactionまでの実行順序を整理します。
状態遷移の不変条件に沿って、関連する更新を一つの処理として扱う範囲を決めます。

Reactionの完了を状態更新・描画・演出のどこまでとするか、キャンセル時に何を保持するかも定義します。
Interactionの終了結果を、SystemFlowが次の経路を選ぶ材料として扱います。
この段階で必要になった機能を基にPort契約へ進みます。

## 4. InteractionからPort契約を導き、Functionを分類する

Interactionに必要な機能から、入力・応答・外部連携の契約を定めます。
引数と戻り値、同期・非同期、失敗・キャンセル、状態へ反映する範囲と所有権を明示します。
必要なアクセスをContextから得るか個別引数で受け取るかを決め、差し替え可能な境界を作ります。

| 分類 | 判断基準 |
| --- | --- |
| Operation | ユーザーの操作・入力を受け取る |
| Reaction | 観測可能な応答と、それに対応する状態変化を提供する |
| Storage | 現在の相互作用の文脈から独立して値を保持・再利用する |
| SilentExternal | ユーザーへの応答や記録を目的としない外部環境との連携 |

可変だからStorage、外部ライブラリを呼ぶからSilentExternal、という分類にはしません。
現在のゲーム状態や表示内容は、まず文脈に属するStateとして検討します。
ユーザー向けの状態変化は、Operation/Reaction内の処理と観測可能な応答に対応させます。
SystemFlowで状態を読むことと、ユーザー向けの文脈を直接書き換えることは分けて判断します。

実行機能の公開境界はPortとして分類し、その実装をExternalに置きます。
ただし全クラスをFunctionにする必要はありません。状態・レイアウト・実装内部の補助は適切な所有者に置きます。
無分類の大きなWindow/Viewサービスへ入力・描画・進行を集める構成は避けます。
一方、Reactionから呼ぶだけのOpen/Closeを別のLifetimeクラスへ転送するなど、
独立した責務・寿命・差し替え理由のない分割も避けます。

Operationが安全な入力アクセスへ委譲するだけでも、実環境とテストを差し替える境界なら役割があります。
すべての補助にinterfaceを作るのではなく、テストや実装の代替が必要な機能境界に置きます。

## 5. 非同期処理の前後を一つの操作として設計する

受付判定と受理、状態遷移と表示更新など、整合性が必要な範囲をまとめて保護します。
ロック中にawait・描画・重い計算を行わず、待機後の反映時に終了意図や処理の有効性を再確認します。
古い待機の後始末で、新しい待機やキャンセル世代を壊さないよう、通知元などを識別します。

キャンセル、ユーザーの終了意図、業務上の失敗は別の状態です。
キャンセルの待機・リセットが成功したことから、ゲーム継続や終了を自動で決めません。
選択前の取り消し、行動確定後の演出中断、セッション終了で何が残るかを仕様として決めます。
ロールバックやユーザーへの表示完了はライブラリが自動で保証するものではありません。

## 6. 終了と失敗の経路を通常経路と一緒に設計する

ReactionEndはReactionが生成し、InteractionEndは相互作用の結果を表します。Contextを結果へ保持しません。
Resultの失敗、送出例外、キャンセルされた非同期結果を混同しません。
実行所有者が処理を停止・待機し、ContextのDisposeをキャンセルや終了待機の代用にしません。

終了時の通知を担うReactionがある場合、先行結果を明示的に渡し、終了・通知の失敗も保持します。
その結果を確定できるなら、独立したOutcome機能や値を重複して増やしません。
CounterではCloseに統合していますが、画面終了と独立した結果通知が必要なら別Reactionも選べます。
起動途中・実行中・終了中の失敗について、どの資源の解放を試み、何を集約するかを決めます。

CounterのSystemFlowによる終了意図・表示の直接更新は、原則からの留保として記録済みです。
次のサンプルで無条件に踏襲せず、必要なら終了要求をOperation/Reactionへ委譲します。
既知の留保は [分析文書](../../InteractionFlow.Samples.Raylib/ARCHITECTURE_ANALYSIS.md) を参照してください。

## 7. 読みやすさと性能を両立する粒度を選ぶ

命名は所有する関心に合わせます。汎用のウィンドウ操作をCounterやFrameという名前に閉じ込めず、
描画ライブラリ依存の型にはその依存が分かる名前を付けます。State・Function・内部補助を区別できる名前を選びます。
意味の切れ目で改行し、長いフローは意図を表す関数へ分けます。

Interactionを個々の弾・座標の更新ごとに増やす必要はありません。
一つの相互作用の内部で大量の要素をまとめて処理し、実行頻度に応じた粒度を選びます。
本体はValueTask<ReactionEnd>を返し、同期結果は直接格納できます。公開ExecuteAsyncはTaskのままです。
通常の値探索は最適化済みですが、繰り返し参照する専用アクセスには型付きプロパティも使えます。

実測で問題になる前にプールや独自スケジューラーを導入しません。
Coreの変更は契約の表現力不足や再利用可能な改善と結び付け、ゲーム固有の都合と分けます。
Counterでは型付きInteractionと追加値検証フックが必要になりました。次もサンプル内のキャストや
隠れた状態管理で埋める前に、利用設計の問題かCore契約の不足かを判断します。

## 初期設計の確認

- 状態ごとの可能な操作、遷移、不変条件、所有・寿命・共有範囲を説明できるか。
- 状態を根拠にSystemFlowを構成し、Interactionの目的と必要なPort契約へ具体化できているか。
- 後続で前提の不足が見つかったときに、状態設計へ戻って整合させているか。
- Programを読まなくてもSystemFlowから体験の進行が分かるか。
- 並行する実行の開始・依存関係・合流・停止・終了待機と、結果集約の責任者を説明できるか。
- 各機能のOperation/Reaction等の分類と、補助クラスの所有者を説明できるか。
- State、アクセス管理、Context、実行所有者の責務と寿命が分かれているか。
- Reactionの完了範囲と、キャンセル後・終了後に残る状態が明確か。
- Portを差し替えて、描画環境なしで進行・失敗・終了・状態の整合性を検証できるか。
- 機能境界に必要な抽象と、役割のない転送・重複が区別できているか。

個別契約: [Context](../CONTEXT_VALUES.md)、[終了結果](../REACTION_RESULTS.md)、[キャンセル](../CANCELLATION.md)。

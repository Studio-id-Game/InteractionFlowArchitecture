# サンプルから得た設計指針

Raylib counter の設計・改修で確認した方向性を、次のサンプルの初期設計に使うためのガイドです。
設計思想・Coreの契約文書を補い、既存契約を変更する文書ではありません。

| 読む文書 | 判断すること |
| --- | --- |
| [InteractionFlowを使うアプリケーション設計](./INTERACTIONFLOW_APPLICATION_DESIGN.md) | 責務分割、Function分類、ContextとState、同期、API利用、検証 |
| [描画ライブラリとの接続設計](./RENDERING_LIBRARY_INTEGRATION.md) | フレーム進行、入力と描画、スレッド、表示状態、演出、終了処理 |

最初に前者で **状態・コンテキスト → SystemFlow → Interaction → Port契約** の順に設計し、
後者で対象の描画環境へ接続します。状態設計には、可能な操作・遷移・不変条件・所有・寿命・共有範囲を含めます。
ユーザー体験の要件を入口とし、後続の制約が見つかったときは状態設計へ戻って見直します。
描画環境がフレームを駆動する方式か、アプリ側でループを所有する方式かも、接続時に判断します。

初期設計では、少なくとも次の内容を短い設計メモとして残してください。

1. 状態・コンテキスト、可能な操作、遷移、不変条件、所有・寿命・共有範囲。
2. SystemFlowが行う選択・反復・終了判断。並行実行がある場合は、依存関係・合流・停止・終了待機・結果集約。
3. 一つのInteractionの目的、操作から明示Reactionまでの流れと完了範囲。
4. Port契約とFunctionの分類、State・アクセス管理・Contextの具体化、補助クラスの責務と同期境界。
5. 入力受付、キャンセル、終了要求、失敗時の扱い。
6. 描画スレッド、フレームと演出の進め方、終了時の待機関係。
7. Port差し替えで確認することと、実画面で確認すること。

これはクラスを増やすためのひな型ではありません。小さな実装から始め、責務と寿命が説明できる構成を選びます。
SystemFlowによる体験上の並行実行の合成と寿命管理は、今後のサンプルで検証を進める方針です。
Counter固有の採用例と留保は [サンプルの分析](../../InteractionFlow.Samples.Raylib/ARCHITECTURE_ANALYSIS.md) を参照してください。

この設計順序を適用した次のゲームのたたき台は、
[一部屋のターン制脱出ゲーム仕様書案](../specs/TURN_BASED_ESCAPE_GAME.md) にまとめています。内容は未確定です。

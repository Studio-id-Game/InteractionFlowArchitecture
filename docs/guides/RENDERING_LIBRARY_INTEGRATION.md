# 描画ライブラリとの接続設計

Raylib counter の改修で得た、フレーム入力・描画・非同期の進行を接続するための指針です。
[InteractionFlowの利用設計](./INTERACTIONFLOW_APPLICATION_DESIGN.md) と合わせて使います。
raylib固有のメインスレッド要件や同期ループの採用を、すべての描画環境へ無条件に適用するものではありません。
利用設計の順序は、状態・コンテキスト → SystemFlow → Interaction → Port契約です。
描画環境の制約によって状態の所有・共有・寿命の前提が変わる場合は、状態設計へ戻って調整します。

## 1. フレームを誰が駆動するか決める

まず描画環境の制約を確認します。

| 確認すること | 設計への影響 |
| --- | --- |
| 自前ループか、エンジンのコールバックか | フレーム反復を直接所有できるか、外部のフレーム通知へ接続するか |
| ウィンドウ・描画・入力のスレッド制約 | 実行スレッドを固定する範囲と確認方法 |
| イベントの配送方式 | ポーリング、通知、非同期Operationの接続方法 |
| 初期化・描画完了・終了の意味 | Reactionの完了範囲と資源の寿命 |

raylibでは、OpenからCloseまでメインスレッドに留めた同期フレーム反復をWindowSystemFlowが所有します。
Programは構成と起動に絞り、DrawFrame / DrawButtonや入力ループを置きません。
エンジン側がループを所有する場合も、コールバックへゲーム進行を散在させず、
外部のフレーム駆動との接続と、SystemFlowの進行判断を分けます。
SystemFlowを、フレームとゲーム進行の並行実行・合流・停止・終了待機を構成する場所としても検証します。
実際の実行機構はTaskや対象環境が担い、そのスレッド制約と待機関係に沿って合成します。

## 2. 入力はOperation、画面への応答はReactionへ置く

| 責務 | Counterでの配置 |
| --- | --- |
| OS終了要求・マウス入力の取得 | RaylibWindowOperation |
| 入力をゲーム側の待機へ配送 | PresentFrame → CounterOperation |
| ウィンドウ生成・描画・終了・結果通知 | RaylibWindowReaction |
| 配置・ヒット判定に共用する描画依存定数 | Externals内部のRaylibLayout |
| 外部APIを持たない開閉状態・所有スレッド情報 | EntitiesのWindowState、フレーム用Contextから提供 |
| 色や揺れなどの描画実装固有の記憶 | Reaction内部のViewState |

Open/Closeは画面の提示・消失に関わるReactionの処理としてまとめられます。
Reactionからの転送しか役割のないLifetimeクラスや、寿命の異なる状態を抱えた大きなViewサービスを増やしません。
独立した資源所有や共有が必要になった場合は、その理由に沿って補助を分けます。
外部APIを使うという理由だけで、画面生成をSilentExternalへ分離する必要はありません。

ネイティブ型、ハンドル、描画APIはExternal側へ閉じ込めます。
Entitiesへ移すのは描画環境から独立した状態・規則です。型名からRaylibを外すだけで依存を隠しません。
WindowOperationは入力と終了要求を扱う名前、RaylibLayoutは実装依存の配置を扱う名前です。

## 3. 一フレームの入力を一か所にまとめる

FrameStateにCommand / CloseRequested / CancelRequestedなど、そのフレームで判断する情報を揃えます。
入力を別のFrameInputへ分けたり、Commandだけ別経路で保持したりする場合は、独立した寿命の理由が必要です。
毎フレーム全項目を上書きし、操作なしならCommandをnullへ戻します。

入力取得、コマンド配送、描画の順序と、終了・キャンセル・通常操作の優先順位を決めます。
CounterではOperationがフレーム情報を記録し、PresentFrameが終了・キャンセル要求のない場合だけ配送します。
表示上のボタン無効化だけに依存せず、受理側でも受付条件を確認します。
処理中の入力を破棄するか、蓄積するか、置換するかはゲーム仕様として明記します。
破棄する場合は、次の入力待ちへ古いコマンドが流れ込まないことを検証します。

## 4. 非同期の進行と描画を安全な状態モデルでつなぐ

描画側のReactionと、ゲーム側の非同期Interactionが、同期されたアクセス管理を共有できます。
WindowOperationは入力トリガー、WindowReactionは描画に集中させ、Operationが描画完了を待つ形を標準にしません。
CounterOperationの薄い委譲は、描画環境なしの入力やテストへ差し替える境界として維持します。

描画側は一貫した表示値を短時間で取得し、ロックを外して描画します。
Counterのように少数の値ならSnapshotのout引数で足ります。
表示値が増えれば専用のスナップショット型も検討できますが、共有可変コレクションをそのまま返すと保護を失います。
各値を個別にロック取得し、異なる時点の状態を一枚の画面へ混ぜないようにします。
入力受付の表示と実際の受理は、同じ判定規則から導出します。

ロック中に描画APIやawaitを実行しません。非同期待機後は終了意図などを再確認して反映します。
描画側が毎フレーム大きな状態を走査・コピーする構成になったら、公開する表示データの粒度を見直します。
スナップショットを作ること自体が目的ではなく、一貫性と短い共有アクセスが目的です。

## 5. 描画スレッドとキャンセルの寿命を明示する

raylibのフレーム内Portは同期完了させ、描画スレッドから非同期継続へ移らないようにします。
ConfigureAwait(false)の有無だけでメインスレッド復帰を保証できるとは考えません。
スレッド制約はWindowState等で検証し、ゲーム側の処理からネイティブ描画APIを呼びません。

Counterはゲーム側だけTask.Runで開始し、フレームと並行実行します。これは採用例であり、
すべてのゲームへTask.Runや専用スレッドを要求するものではありません。
描画ライブラリとゲームの性質に応じて、単一スレッドの進行や別の実行環境も選択できます。

ゲーム処理のキャンセル後も描画を続けたい場合、フレーム側のCancellationを分離します。
親ありFlowContextはCancellationを共有するため、その目的には共有アクセスだけを持つ独立ルートを使います。
Contextの変更・破棄やFunctionのForceResetMemoryStateを、利用中の処理と競合させません。
メインスレッド限定のWindowStateは、背景側へ不用意に提供しません。

## 6. ゲーム状態・表示内容・演出の記憶を区別する

ゲームの結果に関わる状態はEntities、ユーザーへ示す意味のある表示内容は表示State、
補間色・揺れ・直前の描画値など、描画実装のための記憶はReaction内部へ置けます。
描画実装固有の記憶をすべてContextやStorageへ公開する必要はありません。
逆に、入力判定や進行判断に使う値を描画側の私有状態へ隠しません。

演出はフレーム回数ではなく経過時間を基準に進めます。
Counterの減衰なら、60FPSでの毎フレーム0.9倍を `Pow(0.9, elapsedSeconds * 60)` に換算しています。
新しい演出なら秒数・速度を基準に設計します。ゲーム進行の時間と演出時間を同一にする必要はありません。
リセット時は演出の記憶も初期化し、別セッションへ前回の値を持ち越さないようにします。

## 7. 状態更新完了・描画完了・演出完了を区別する

CounterReactionの完了は表示データの更新、WindowReactionの完了はEndDrawingまでです。
この構成は各更新が必ず一度描画されることを保証せず、終了直前の表示が描かれない場合もあります。
APIの処理完了は、ユーザーが実際に認識したことの保証でもありません。

次のゲームでは、勝敗画面や移動演出をどこまで待つかを最初に決めます。
提示・演出の完了通知が必要なら、対象の処理・セッションを識別し、キャンセルと終了時の解除も設計します。
その追加同期をすべてのReactionへ一律に導入する必要はありません。

特に、メインスレッドがゲーム終了を同期的に待ち、ゲーム側が次の描画を待つ循環を作らないことが重要です。
提示完了を待つ仕様なら、待機中も必要なフレームを進めるか、終了前に待機を解除するなど、
終了手順を含めて待機関係を成立させます。

## 8. 起動失敗と終了処理を最初から扱う

SystemFlowが起動結果、フレーム結果、ゲーム結果、終了待機の失敗を集め、
CloseのReactionへ先行結果を明示的に渡す構成を使えます。
Closeは画面の終了・結果通知を行い、自分の失敗も先行結果へ合成します。
起動途中の失敗でも、実際に確保した資源に応じて解放を試みます。
ReactionのCloseを呼んだだけで、別の非同期処理の終了まで保証されたとは扱いません。

終了時に、入力受付の停止、必要なキャンセル通知、実行の待機、ネイティブ資源の解放を誰が担当するか決めます。
Counterの順序をコピーする前に、背景処理が描画資源やフレーム進行に依存するか確認します。
ウィンドウの閉じる操作やEscはOperationで取得した要求であり、アプリ全体の終了判断はSystemFlowの責務です。

## 初期設計と検証の確認

- 入力・描画・進行・状態の配置が、Programや一つのViewへ集中していないか。
- フレーム駆動方式、スレッド、Context共有範囲、実行所有者が明確か。
- 無入力・連打・処理中・キャンセル・終了で入力がどう扱われるか。
- Snapshotの一貫性と、描画中にロックを保持しないことを確認できるか。
- 状態更新、描画、演出のどこまでをReaction完了とするか。
- 起動・実行・通知・Closeの失敗や、終了時の待機関係をPort差し替えで検証できるか。
- 実画面では、入力待ち中・非同期処理中の描画継続、演出、リトライ、終了を確認できるか。

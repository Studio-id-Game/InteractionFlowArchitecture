# 一部屋のターン制脱出ゲーム — 仕様書案

状態: 初版実装済みの仕様書案。ゲーム内容・配置・キー・演出時間は本書の提案を初版に採用しています。
設計判断と検証結果は [サンプルREADME](../../InteractionFlow.Samples.EscapeGame/README.md) を参照してください。

## 1. 目的と設計の前提

小さなゲームを通じて、InteractionFlowによる複数の状態と相互作用の設計を検証します。
設計順序は **状態・コンテキスト → SystemFlow → Interaction → Port契約** です。
基準は [利用設計ガイド](../guides/INTERACTIONFLOW_APPLICATION_DESIGN.md) と
[描画接続ガイド](../guides/RENDERING_LIBRARY_INTEGRATION.md) です。

| 合意済みの方向性 | 本書で具体化する案 |
| --- | --- |
| 状態設計を土台に、フローから機能契約を導く | 部屋・プレイヤー・所持品・仕掛け・敵・操作段階を扱う |
| SystemFlowの進行・合成・実行寿命管理を活用する | フレーム描画とゲーム進行を並行させ、ターン内は逐次合成する |
| プレイ中のポーズ・再開を提供し、Flow全体の制御を検証する | ゲーム進行と演出時間を協調停止し、描画・再開・終了の受付は継続する |
| 機能分離・可読性・保守性・代替性を優先する | 一部屋、一体の敵、一個の鍵、一個のスイッチ、一個の扉 |
| 実用上の必要性からAPIを検証する | 新しい汎用スケジューラーやCore APIは初期要件にしない |

### 検証項目

| ID | 検証したいこと | ゲーム上の検証場面 |
| --- | --- | --- |
| V1 | 関心別Stateと複数状態の整合性 | 移動と鍵取得、鍵消費と解錠、位置と捕獲判定 |
| V2 | 状態に基づくSystemFlowの選択・反復 | 操作選択、プレイヤー行動、敵行動、勝敗、リトライ |
| V3 | 並行実行と寿命の合成 | 描画継続とゲーム側の入力待機・演出待機、終了時の合流 |
| V4 | 選択・確定・演出省略・終了の区別 | 選択取消は状態を消費せず、確定後の結果は演出省略でも残る |
| V5 | Contextの提供範囲と寿命 | アプリ・セッション・一回の行動、古い通知の遮断 |
| V6 | 明示Reactionと完了範囲 | 状態更新後の提示要求、演出完了通知、勝敗画面の保持 |
| V7 | 描画を代替した検証 | fake Portで入力、時間進行、描画通知、失敗を制御 |
| V8 | Flow全体のポーズ・再開 | 入力待ち・プレイヤー演出・敵演出で停止し、同じ状態と実行から再開する |

## 2. 状態・コンテキスト設計

### 2.1 ゲーム概要と初期状態

プレイヤーは鍵を拾い、スイッチを作動させ、鍵を使って扉を開け、出口へ到達します。
有効なプレイヤー行動の後に、敵が巡回経路を一マス進みます。敵と同じマスに入ると敗北します。
思考時間の制限、乱数、HP、攻撃、成長、スコア、セーブ、複数ステージは初版の対象外です。

盤面は7列×5行。座標は左上(0,0)、右が+x、下が+y。上下左右の移動のみで斜め移動はありません。

```text
   0123456
0  #######
1  #K.G#X#
2  #....D#
3  #P.S..#
4  #######
```

| 記号 | 意味・初期値 |
| --- | --- |
| # / . | 壁 / 通路 |
| P | プレイヤー(1,3) |
| K | 鍵(1,1)。未取得、所持数0 |
| S | スイッチ(3,3)。未作動。隣接マスから操作し、一度作動すると維持 |
| D | 扉(5,2)。施錠中。スイッチ作動済みかつ鍵所持で、隣接マスから解錠できる |
| X | 出口(5,1)。唯一の進入経路は扉(5,2) |
| G | 敵(3,1)。経路(3,1)→(3,2)→(2,2)→(2,1)→(3,1)を巡回 |

プレイヤーも敵も一行動で最大一マス動きます。敵はプレイヤーを追跡しません。
閉じた扉と壁への移動は無効です。開いた扉・作動済みスイッチ・取得後の鍵マスは通行できます。
出口・鍵・スイッチのマスも通行可能です。敵の巡回経路は壁・扉・出口を通りません。

### 2.2 論理状態の関心

次の分担を初期案とします。各項目を必ず独立クラスにする必要はありません。
複数状態の協調更新はアクセス管理に置き、State自身は値・規則を担当します。

| 関心 | 主な値・規則 | 寿命 |
| --- | --- | --- |
| 部屋定義 | 地形、鍵・仕掛け・出口の配置、敵巡回経路。実行中は不変 | アプリ |
| プレイヤー | 位置 | セッション |
| 所持品 | 鍵の有無 | セッション |
| 仕掛け | 鍵の取得状態、スイッチ作動、扉の解錠 | セッション |
| 敵 | 位置、巡回経路のインデックス | セッション |
| 進行 | セッションID、ターン番号、操作段階、Outcome | セッション |
| 実行制御 | Active / Paused / Stopping、ポーズ前の進行を保持する制御情報 | セッション |
| 選択 | 仮選択した行動と対象、受付中の入力待機 | 一回の行動選択 |
| 表示 | スナップショットの版、メッセージ、受付可能な操作、提示要求 | セッション |
| 提示管理 | 演出ID、進行中の提示、完了・省略・停止の通知 | 提示要求 |
| ウィンドウ | 開閉、所有スレッド、当該フレームの入力 | アプリ / フレーム |

OutcomeはRunning / Won / Lostです。通常の敗北はゲーム上の結果であり、Resultの失敗にしません。
アプリ終了要求はこれとは独立した、単調な終了意図として保持します。
実行障害は先行失敗の集約対象とし、ゲーム上のLostに変換して隠しません。

### 2.3 操作段階と遷移

| 段階 | 可能な操作 | 次の段階 |
| --- | --- | --- |
| Preparing | 終了のみ | 初期化と初期提示の完了後にSelecting |
| Selecting | 仮選択、確定、選択取消、終了 | 有効な確定でPlayerPresenting |
| PlayerPresenting | 演出省略、終了 | 提示完了後、OutcomeがRunningならEnemyPresenting、他はResult |
| EnemyPresenting | 演出省略、終了 | 敵行動と提示の完了後、RunningならSelecting、他はResult |
| Result | 結果提示完了後にリトライ、終了は常時 | リトライで旧セッションを終了し、新しいPreparingへ |
| Stopping | 新規操作なし | 待機解除・終了合流・Close |

段階・Outcome・表示受付条件は、整合性のある更新単位で反映します。
PlayerPresentingはプレイヤー行動確定後の段階です。EnemyPresentingへの移行は敵行動の確定と一緒に行います。
Resultへの移行と勝敗表示の設定は、結果通知Reactionが行います。
Selecting / PlayerPresenting / EnemyPresentingではポーズ操作も受け付けます。
Pausedはこれらに重なる実行制御状態で、停止中に可能な操作は再開と終了だけです。

### 2.4 行動と更新範囲

| 行動 | 有効条件 | 確定時の更新 |
| --- | --- | --- |
| 一マス移動 | 隣接先が通行可能 | 位置。未取得の鍵マスなら鍵取得も同時更新 |
| スイッチ操作 | 隣接し、未作動 | 作動状態 |
| 扉の解錠 | 隣接、施錠中、スイッチ作動済み、鍵あり | 鍵消費と解錠を同時更新 |
| 待機 | SelectingでOutcomeがRunning | 位置等を維持してターンを消費 |

有効な行動の確定時だけターン番号を1増やします。無効操作・仮選択・選択取消では増やさず、敵も動きません。
行動の有効性は仮選択時と確定時に確認します。確定処理はアクセス管理内で検証と更新を一括実行します。
移動後のマスに敵がいればLost、出口ならWonです。プレイヤー行動で勝敗が決まった場合、敵の行動は行いません。
それ以外はプレイヤー提示完了後に敵が一マス進み、移動先がプレイヤーならLostです。
プレイヤーが敵のいるマスへ移動した後で敵を動かして捕獲を回避する、という解釈はしません。

### 2.5 不変条件

1. プレイヤー・敵の位置は盤面内の通行可能なマスにある。閉じた扉にプレイヤーはいない。
2. 鍵は一個で、未取得・所持・消費済みのいずれか。再取得・二重消費はできない。
3. 解錠済みならスイッチ作動済み、鍵取得済み・消費済み。解錠後に再施錠しない。
4. Outcomeはセッション内でRunningからWonまたはLostへだけ変化する。
5. 行動選択の受付はSelectingかつOutcomeがRunningかつ実行制御がActiveかつ終了要求なしの場合だけ。演出・ポーズ中は通常行動を蓄積しない。
6. 状態の確定と対応する表示版・提示要求を同じ更新範囲で公開する。
7. 行動確定後は、演出省略やキャンセルで確定済みの位置・鍵・仕掛け・ターン数を巻き戻さない。
8. 終了要求後はキャンセルのリセット等で入力受付に戻らない。
9. 通知はセッションIDと提示IDが一致する待機だけを完了させ、完了処理は冪等とする。
10. 確定状態の共有アクセスは共通の同期境界で扱い、描画・await・外部通知をロック内で実行しない。
11. Pausedが成立した後は、行動・敵移動・ターン・操作段階・仮選択を進めず、ゲーム演出の時間と新しい完了通知も進めない。終了・障害に伴う停止と後始末は例外とする。
12. ポーズと再開だけでセッションID、ターン数、提示ID、ゲーム用Cancellationの世代を変更しない。

### 2.6 ポーズ・再開の状態と意味

ポーズは操作段階・Outcomeとは独立した実行制御状態とします。
Selecting / PlayerPresenting / EnemyPresentingでポーズでき、操作段階自体は維持します。
Preparing / Resultではポーズを受理せず、Stoppingから再開はできません。
勝敗確定済みでも、結果画面へ移る前の行動演出中はポーズできます。

| 停止時点 | 保持するもの | 再開時の動作 |
| --- | --- | --- |
| 操作入力待ち | 仮選択、既存の入力待機、未適用の受理済み入力があればその一件 | 選択の続きから進める。新しい入力の蓄積はない |
| 行動確定の直前・直後 | 一括更新の前か後の整合した状態、未適用の確定要求または確定済み結果 | 未適用なら一度だけ確定、適用済みなら二重適用せず提示の続きを進める |
| プレイヤー・敵の演出中 | 確定済み論理状態、提示ID、演出の経過時間と表示位置 | 残り時間の演出を継続する |
| 提示完了と次段階の間 | 受領済みの完了結果、現在の段階 | 再開後に一度だけ次段階を選ぶ |

ポーズ成立時点は、制御Reactionが共有アクセスの同期境界でPausedを適用した時点です。
実行中の短い一括更新は完了してから停止し、更新の途中でスレッドを強制停止しません。
入力した瞬間から適用までに先行処理が完了する場合はありますが、成立後のゲーム更新は止めます。
停止中も盤面の現在表示とポーズ表示、再開・終了ボタンの描画と入力は継続します。
ポーズ表示のためのUI演出は独立した実時間で進めてもよく、ゲーム演出の時間へ加算しません。

再開ではActiveへ戻し、同じセッション・実行・提示を継続します。
待機をキャンセルして最初から起動し直す方法や、CancellationObjectのリセットによる代用はしません。
ポーズ中の終了・実行障害は通常の停止経路へ移り、再開を待たずに終了待機を解除します。

### 2.7 Contextと提供するアクセス

EscapeApplicationContextは、Input / World / Display / Presentation / Controlの用途別アクセスを提供します。
ポーズの制御状態と協調待機へのアクセスも提供しますが、Context自身がフローを停止・再開する処理は持ちません。
Worldは複数Stateを整合して更新する入口で、生の共有可変Stateや可変コレクションを外へ返しません。
Displayのスナップショットには、盤面・位置・仕掛け・段階・選択・メッセージ・版を一貫した形で含めます。
色・ピクセル座標・ネイティブハンドルは含めず、表示の意味と描画実装を分けます。
Contextは値へのアクセス・スコープを管理し、Task起動やフローの進行を担当しません。

| スコープ | 共有するもの | 独立させるもの |
| --- | --- | --- |
| アプリ | 部屋定義、アクティブセッションへの安全なアクセス、終了意図 | ウィンドウ用とゲーム実行用のCancellation |
| セッション | 論理State、表示、入力受付、提示通知管理 | セッションID、全可変状態。リトライでは新規作成 |
| 一回の行動 | セッションのアクセス、ゲーム側Cancellation | 仮選択・確定した行動の情報 |
| フレーム | アクティブセッションの表示・入力接続 | フレーム入力、WindowStateはメインスレッド限定 |

アクティブセッションの差し替えは専用アクセス管理で行い、実行中のContext.Withの書き換えで表現しません。
旧セッションの待機を閉じてから新セッションを公開します。各入力・提示通知は取得時のセッションIDを付けます。
Contextを破棄する前に、そのContextを使う実行と待機が完了していることを実行所有者が確認します。
固定アクセスのプロパティとTryGetCoreは同じ対象を返し、破棄後の新規取得は拒否します。
Withによる固定アクセスの隠蔽とEntry経由の差し替えも、Context固有の検証で拒否する案とします。

## 3. SystemFlow設計

### 3.1 並行実行と所有者

```text
Program
  └─ WindowSystemFlow（メインスレッド、アプリ全体の実行所有者）
       ├─ OpenWindow
       ├─ GameSystemFlow（Task.Runで一度起動、ゲーム全体）
       │    └─ SessionSystemFlow（初期化→ターン反復→結果入力→終了）をリトライごとに実行
       │         └─ TurnSystemFlow（選択反復→プレイヤー行動→敵行動）
       ├─ PresentFrameを反復（ゲーム側の入力・提示待ち・ポーズ中も継続）
       │    └─ フレーム結果の制御要求を受け、ChangeControlを実行
       └─ 終了要求の適用→キャンセル→GameSystemFlowの合流→CloseWindow
```

SystemFlowは実行方針を構成し、Taskや描画環境が実行機構を担います。
GameSystemFlowは同時に一つだけ起動します。敵行動はターン内で逐次合成し、敵ごとのTaskは作りません。
ゲーム側はraylibを呼ばず、フレーム側は非同期の提示完了を同期的に待ちません。

### 3.2 ターンとセッションの進行

1. 初期化Reactionがセッションを公開し、初期状態の提示を要求する。ゲーム側は提示完了を待つ。
2. 選択Interactionを繰り返し、有効な行動が確定されたらプレイヤー行動Reactionを実行する。
3. プレイヤー行動Reactionが状態を一括更新し、演出提示の完了を待って終了する。
4. SystemFlowがOutcomeを参照し、Runningなら敵行動Interactionを実行する。
5. 敵行動Reactionが状態・捕獲判定を更新し、演出提示の完了を待って終了する。
6. Runningなら次の選択へ戻る。Won/Lostなら結果Reactionで結果画面を提示する。
7. 結果画面はリトライまたは終了の入力まで保持する。勝敗が決まっただけでフレームループを終了しない。
8. リトライは旧セッション終了Reactionを経て、新しいIDと状態でやり直す。

終了要求または実行障害があれば、通常の次段階へ進まず、共通の停止経路へ移ります。
SystemFlowは状態・結果から経路を選び、ユーザー向けの状態更新はReactionへ委譲します。

### 3.3 Flow全体の協調的なポーズ制御

WindowSystemFlowはPresentFrameが取得したポーズ・再開要求を受け、ChangeControl Interactionを実行します。
この制御経路は通常のゲーム入力Operationや演出完了待機から独立させ、
ゲーム側がそのどちらを待っていても操作できます。Interaction同士を直接ネストしません。
ポーズ表示の適用は次の描画で確認できます。
制御要求もセッションIDを持ち、対象の段階とセッションを適用時に再確認します。
同じフレームでリトライ等により対象が変わっても、新しいセッションへ古いポーズを適用しません。

Game/Session/TurnSystemFlowは、次の相互作用や段階へ進む境界で再開待機を行います。
待機済み入力や提示結果の受領と、次のゲーム処理への適用も分けます。
ただしSystemFlow側での事前確認だけでは、確認直後のポーズと競合します。
アクセス管理の行動確定・段階更新も、Pausedかどうかの確認と一括更新を同じ同期境界で行います。
停止により未適用となった仕事は呼び出し側が保持し、再開後に再検証して一度だけ適用します。

進行中のReactionは協調的に待機してよく、ポーズのために終了結果を生成したり再実行したりしません。
提示側も停止状態に従ってゲーム演出と新規の完了通知を止めます。
成立前に完了済みの通知や後始末は取り消さず、再開後のゲーム進行だけをゲートします。
したがって全Taskを物理的に停止する保証ではなく、ゲーム進行全体を整合して停止する保証です。

再開待機はロックを外して非同期に行い、ゲーム用Cancellationで必ず解除できるようにします。
終了意図をPausedより優先し、停止Reaction・キャンセル・合流・Closeは再開待機の対象にしません。
SystemFlow基底に新たな汎用ポーズAPIがあるとは仮定せず、サンプル側の制御契約として検証します。

### 3.4 循環待機を作らない終了手順

フレームループは通常、勝敗や演出待ちでは停止しません。
OS終了要求・終了ボタン・ゲーム側の終了選択・実行障害で停止に入る場合は、以下を守ります。

1. 独立した停止用Contextで終了Reactionを実行し、終了意図を保持して通常入力を閉じる。
2. 提示管理を停止し、未完了の提示通知を解除する。以後の提示要求は直ちに停止結果になる。
3. ゲーム用Cancellationへ通知し、入力待ち・演出待ちを終了させる。
4. GameSystemFlowを待ち、後始末と失敗を集約する。この時点でゲームは次フレームに依存しない。
5. CloseのReactionがネイティブ資源を解放し、先行失敗とClose・通知の失敗を保持して終了する。

停止Reactionの実行失敗時もキャンセル・合流・Closeを試みます。
提示通知の停止結果は演出完了の成功と区別し、終了意図を確認して次の行動へ進まないようにします。
提示待機はゲーム用トークンでも解除できる契約にし、提示管理の停止失敗だけで待ち続けないようにします。
停止用ContextのDisposeでは停止・待機を代行しません。失敗集約は確定した待機対象の完了後に行います。

## 4. Interaction設計

名称は仮称です。共通の目的と完了範囲が一致する処理は統合できます。

| Interaction | Operation / Reaction | 完了範囲 |
| --- | --- | --- |
| OpenWindow / PresentFrame / CloseWindow | ウィンドウ操作・描画・結果通知 | メインスレッドの同期フレーム処理と資源管理 |
| BeginSession | セッション初期化Reaction | 初期状態を公開し、最初の提示完了まで |
| SelectAction | ゲーム入力Operation→選択Reaction | 仮選択、取消、確定要求、無効操作のフィードバックまで |
| ApplyPlayerAction | 行動Reaction | 再検証・確定・状態更新・提示完了まで |
| ApplyEnemyAction | 敵行動Reaction | 移動・捕獲判定・状態更新・提示完了まで |
| ShowResult | 結果Reaction | 結果段階の設定と結果画面の提示まで |
| SelectAction（結果段階でも共用） | 結果入力Operation→応答Reaction | リトライの意図を記録するまで。終了は独立した制御経路 |
| ChangeControl | 制御Reaction | 可能な段階でPaused/Active、または現在の提示の省略を適用するまで。再開待機は行わない |
| EnableSelection / EnableResultInput | 受付開始Reaction | 必要な提示完了後、段階と受付可能性を更新するまで |
| EndSession / RequestShutdown | 寿命終了・停止Reaction | 入力・提示の閉鎖と必要な応答まで。Task合流はSystemFlowの責務 |

全Interactionは明示Reactionの終了結果で完了し、他のInteractionを直接実行しません。
ゲーム上の行動結果・勝敗・リトライ選択は文脈値で提供し、ReactionEndやInteractionEndへ独自Contextを格納しません。
本体はValueTask<ReactionEnd>、公開実行はTask<InteractionEnd>という現行契約を使用します。

## 5. Port契約と描画接続

### 5.1 機能契約案

| Port | 分類 | 契約の要点 |
| --- | --- | --- |
| IWindowOperation | Operation | フレーム入力・閉じる要求を同期取得し、毎フレーム全項目を上書き |
| IGameOperation | Operation | セッションID付き入力を受理・配送。ゲーム側は非同期に一件待機 |
| IWindowReaction | Reaction | Open / Draw / Close。Drawは一貫した表示を取得し描画後に提示進行を報告 |
| IGameReaction | Reaction | 初期化・選択・プレイヤー行動・敵行動・結果表示を、状態更新と提示待機へ接続 |
| ISessionReaction | Reaction | セッション終了・アプリ停止の意図を適用し、入力と提示を閉じる |
| IGameControlReaction | Reaction | ポーズ・再開を同期適用。状態更新と提示制御を共通の境界で行い、描画を待たない |
| 共通例外・キャンセルPort | Reaction | 実行障害の保持、後始末、キャンセル結果の処理 |

ゲーム入力は、そのセッションで対応するOperationの待機が有効な場合だけ受理し、先行入力を蓄積しません。
結果段階でも、結果提示の完了後に結果入力Operationが待機するまではリトライを受理しません。
セーブや文脈から独立した記録はないため、初版ではStorageを追加しません。
単にraylibを呼ぶという理由でSilentExternalへ分割しません。
独立した役割のないWindow/View/Lifetime/Outcomeサービスを追加せず、内部補助として構造化します。
Portは専用Contextを受け取り、Input / World / Display / Presentationを介して実行します。
共通HandlerはIFlowContextのままでもよく、必要なアクセスをGetRequiredで取得します。

### 5.2 提示要求と演出

提示要求にはセッションID、提示ID、表示版、演出種別、開始・終了位置等の意味上の情報を持たせます。
フレームのReactionは経過時間から演出を進め、最終表示のEndDrawing後に完了を報告します。
ゲーム側のReactionはその通知を非同期に待ちます。通常進行では提示要求は一件ずつで十分です。
状態更新は先に確定し、描画側だけが開始位置から確定位置へ補間します。
最初のフレーム取得時を演出開始とし、既に提示済みの古い要求を再演しません。
ポーズ中は現在の補間位置を保ち、ポーズ中の実時間をゲーム演出の経過時間へ加算しません。
初版では、制御版が変わった境界フレームのdeltaを破棄します。ポーズ区間の混入を防ぐため、
最大一フレーム分の動作時間も捨て得る保守的な時間処理を採用します。
最終フレームを描画してもPaused成立後は新しいゲーム提示完了を報告せず、再開後に一度だけ報告します。
報告時も共有アクセスの同期境界で制御状態を再確認し、ポーズ前に取得した表示だけを根拠に完了させません。

移動・敵移動は各0.15秒、解錠・スイッチは0.2秒、待機・選択変更・結果画面は最終表示一回を初期案とします。
最終表示一回を待つのは初期提示・行動・結果画面です。通常の仮選択応答は表示更新までで完了してよいものとします。
表示が画面に提出されたことを確認する契約で、ユーザーの認識自体を保証するものではありません。
色・揺れ・補間時間等はRaylibWindowReactionの内部状態に置き、経過秒数を基準に進めます。

### 5.3 入力とキャンセル案

| 入力 | Selecting | 演出中 | Result |
| --- | --- | --- | --- |
| 矢印 / WASD | 移動方向を仮選択。無効なら選択を空にして理由表示 | 破棄 | 破棄 |
| E | 隣接する未作動スイッチ / 解錠可能な扉を仮選択 | 破棄 | 破棄 |
| Space | 待機を仮選択 | 破棄 | 破棄 |
| Enter / 確定ボタン | 選択中の有効行動を確定 | 破棄 | 破棄 |
| Esc / 取消ボタン | 仮選択を空にする。ターン非消費 | 破棄 | 破棄 |
| F / 演出省略ボタン | 破棄 | 現在の演出を最終表示へ進め、描画後に完了通知 | 破棄 |
| R / リトライボタン | 破棄 | 破棄 | 新規セッションへ |
| P / ポーズボタン | ポーズ要求 | ポーズ要求 | 破棄 |
| 終了ボタン / OSの閉じる操作 | 終了要求 | 終了要求 | 終了要求 |

Eの対象がなければ選択を空にし、理由を表示します。初期盤面では複数対象への隣接は発生しません。
EscはCounterの終了操作から変更し、ゲームの選択取消に使用します。
Fによる演出省略はCancellationObjectのキャンセル・リセットを使わず、現在の提示IDだけに作用します。
ポーズ中はP / 再開ボタンと終了操作だけを受理し、移動・確定・取消・演出省略・リトライは破棄します。
再開と同フレームの通常入力も破棄し、再開後の新しい押下から受付を始めます。
アプリ終了時のキャンセルは、入力待ち・提示待ちを解除する実行制御です。ゲーム上の選択取消と区別します。
同フレームの優先順位は終了→ポーズ/再開→演出省略/選択取消→通常操作とし、矢印等の同時押しは上→右→下→左、
その他の同時押しはE→Space→移動→確定の順に一件だけ配送します。無効操作も後から再配送しません。
連打・キーリピートで複数ターンを消費しないよう、押下エッジのみを入力とします。
画面には盤面・仮選択の対象・鍵/スイッチ/扉・ターン番号・敵の巡回方向・可能な操作・メッセージを表示します。

## 6. 検証と受け入れ条件

### 6.1 描画なしの自動検証

| 対象 | 受け入れ条件 |
| --- | --- |
| 初期化・リトライ | 全状態が初期値になり、セッションIDが更新される |
| 選択・取消 | 確定前は位置・仕掛け・ターン数・敵位置を変更しない |
| 無効操作 | 壁・閉扉・条件不足の解錠は無効で、敵が動かない |
| 鍵・解錠 | 取得の二重適用、鍵だけ消費、解錠だけ成立する中間状態を観測しない |
| ターン進行 | 有効行動一回に敵行動が最大一回。勝敗確定後は敵を動かさない |
| 捕獲 | プレイヤー進入・敵進入の両方でLost。終了したセッションをRunningへ戻さない |
| 提示完了 | 初期・行動・勝敗表示の必要な提示完了前に次の段階へ進まない |
| 演出省略 | 確定済み論理状態を維持し、最終フレーム提出後に待機を完了 |
| 古い通知 | 旧セッション・旧提示・重複通知が新しい待機を完了させない |
| 並行性 | 入力待ち・演出待ちでもフレームを進められ、ロック越しに整合した表示を取得できる |
| ポーズ受付 | 入力待ち・プレイヤー演出・敵演出のどこからでも独立した制御経路でポーズできる |
| ポーズ維持 | 成立後は状態・ターン・仮選択・敵行動・ゲーム演出時間・新しい提示完了が進まない。描画は続く |
| 再開 | 同じセッション・待機・提示から継続し、行動確定・敵行動・提示通知を二重適用しない |
| 競合 | 確定・提示完了・次段階移行とポーズを制御した順序で競合させ、一括更新の前か後だけで停止する |
| ポーズ中の終了・障害 | 再開せずキャンセル・再開待機解除・合流・Closeまで完了する |
| 終了 | 各待機段階で終了要求を入れても循環待機・未完了Taskを残さない |
| 障害 | 起動・描画・提示通知・ゲーム処理・Closeの失敗を保持し、可能な後始末を実行する |

提示進行と入力通知はfake Portで制御し、実時間のsleepに依存せず待機順序を確認します。
同じ入力列の途中にポーズと長い仮想時間経過を挿入しても、再開後のゲーム結果とターン数が一致することを確認します。
ポーズ中のキー連打、繰り返しのポーズ・再開、無効段階でのP、旧セッションの制御要求も検証します。
解法の一例: 上→上(鍵)→下→下→右→E(スイッチ)→右→右→右→E(扉)→上→上(出口)。
各矢印とEは仮選択後に確定し、演出完了を通知するものとします。この列は12ターンでWonになり、
終端では鍵消費済み・スイッチ作動済み・扉解錠済み・敵の追加行動なしを確認します。

### 6.2 実画面での確認

入力待ち・演出待ちでも描画が継続すること、仮選択と確定の違いが分かること、
FPSが変わっても演出時間が大きく変わらないこと、演出省略、捕獲・脱出、結果画面保持、
リトライ後の初期化、入力待ち・演出中の終了を確認します。
ポーズ表示、選択保持、補間位置の停止、再開時の時間の飛びがないこと、ポーズ中の終了も確認します。
全ネイティブ入力・描画・Closeはメインスレッドで実行し、所有スレッド違反を検出します。

### 6.3 性能確認

多数のエンティティやマルチコア性能の検証を目的にせず、常時描画と低頻度のターン進行を対象とします。
実装後にフレーム当たりのInteraction回数・割り当て・時間を測り、基盤コストと描画・演出コストを分けます。
性能だけを理由に機能境界を消さず、不要な一時オブジェクトや過剰なスナップショット生成から確認します。
提示通知の追加に伴うコストも記録します。Counterの計測値をゲーム全体の性能保証にしません。

## 7. 実装順序とレビュー事項

1. 盤面、State、遷移、不変条件、既知の解法を描画なしで検証する。
2. Context・アクセス管理と、逐次ターンのSystemFlow/Interaction/Portを構成する。
3. fake描画を使って、入力・提示待ち・ポーズ/再開・リトライ・終了合流を検証する。
4. raylibの入力・描画・経過時間による演出へ接続する。
5. 実画面確認と計測を行い、Coreの不足があればサンプル固有の都合と区別して記録する。

初版に採用した提案は、盤面と敵巡回、全行動の仮選択・確定方式、Esc/Fの用途、
提示完了を待つ範囲です。これらを変更する場合は、状態とフロー、受け入れ条件を一緒に見直します。
初版でセーブ、複数敵、攻撃、ランダム生成、汎用描画エンジン、提示通知のCore標準化は行いません。
